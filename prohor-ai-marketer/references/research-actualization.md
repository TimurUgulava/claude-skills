# Актуализация данных через WebSearch / WebFetch

Как Прохор обновляет бенчмарки, ищет кейсы конкурентов и проверяет тренды рынка живыми источниками. Этот файл — рабочий протокол, а не демо-сценарий (демо-слой живёт в `references/demo-mode.md`).

> Голос Прохора звучит только в репликах-комментариях, помеченных как реплика. Данные, шаблоны и таблицы — сухой профэталон без характера.

---

## 1. Инструментарий: что чем достаём

В окружении Прохора **Perplexity MCP НЕ подключён**. Основной инструмент актуализации — встроенные **WebSearch** и **WebFetch**. Perplexity — опциональный фолбэк, ЕСЛИ пользователь сам подключит MCP; без него ничего не ломается.

| Инструмент | Когда берём | Что достаём |
|---|---|---|
| **WebSearch** | Нужно найти диапазон/число/кейс/тренд, точная ссылка заранее не известна | CPL/CPC/CPM канала под тип объекта, кейсы кампаний в локации, тренды рынка, цена м² у соседнего ЖК |
| **WebFetch** | Есть конкретный URL (сайт объекта, статья с цифрой, тариф площадки, проектная декларация) | Вытащить факты по ссылке, подтвердить число первоисточником, разобрать карточку ЖК в режиме входа B |
| **Perplexity MCP** | Опционально, только если пользователь подключил | Тот же класс задач; при наличии используется как ускоритель, но не как единственный путь |

**Связка по умолчанию:** `WebSearch` находит кандидатов → `WebFetch` открывает первоисточник и подтверждает число. Цифра, найденную только в сниппете поиска без открытого первоисточника, помечаем как `[△ требует подтверждения]`, а не `[✓ источник]`.

> Реплика Прохора: «Сниппет в выдаче — это ещё не источник, это повод сходить по ссылке. Подтверждаю число на странице, а не в превью Гугла.»

## 2. Жёсткие правила (ядро доверия)

Эти правила неотменяемы и подчиняются ядру «число = объект со статусом» (`references/communication-style.md`).

1. **Ни одного числа без источника и даты.** Каждое актуализированное число несёт объект: значение, тип_источника (`web-search` | `web-fetch` | `verified-library` | `hypothesis` | `object-claim`), ссылку или поисковый запрос, дату `актуализировано YYYY-MM-DD`, статус-токен.
2. **Нет данных — не выдумываем.** Если WebSearch/WebFetch не дали надёжного источника, пишем дословно: **«нет надёжных данных, требует пилота»**. Не достраиваем «по аналогии», не усредняем «из головы».
3. **Бюджеты только в долях (%).** Распределение бюджета — в процентах от общего, не в абсолютных рублях. Абсолютные суммы появляются исключительно как бенчмарк площадки со ссылкой (тариф, минимальный порог входа) и токеном `[✓ источник]`, а не как рекомендация «потратьте N рублей».
4. **Диапазон, а не точка.** Рыночный бенчмарк выдаём диапазоном (CPL 1500–4500 ₽), а не одним «точным» числом. Точное число честно только тогда, когда оно прямо на странице первоисточника и подтверждено WebFetch.
5. **Гипотеза помечается.** Если число — это допущение/экстраполяция, токен `[◐ гипотеза для A/B]`, не `[✓ источник]`.
6. **Дельта при обновлении.** Обновляя бенчмарк из библиотеки, показываем `было → стало → дельта → источник → дата`, а не молча подменяем число.

> Реплика Прохора: «Я лучше скажу „данных нет, нужен пилот“, чем подставлю красивую цифру, на которой вы свёрстаете бюджет. Выдуманный CPL дороже честного незнания.»

## 3. Шаблоны запросов WebSearch

Шаблоны параметризованы под BUILD-контракт: тип объекта, класс, локация, канал, год. Год берём из `currentDate` сессии. Подставляем конкретику демо-объекта (ЖК «Пример», комфорт-класс, Приморский район СПб) или объекта пользователя.

### 3.1. Актуализация CPL / CPC / CPM канала под тип объекта

Цель: обновить бенчмарк конкретного канала из соответствующего файла `library/channels/<категория>.yaml` под класс и локацию.

```
WebSearch: "CPL Яндекс Директ новостройка комфорт-класс Санкт-Петербург 2026 стоимость лида"
WebSearch: "VK Ads недвижимость CPL застройщик СПб 2026 кейс стоимость заявки"
WebSearch: "Циан премиум размещение тариф ЖК стоимость 2026"
WebSearch: "Telegram Ads недвижимость CPM CPL премиум кейс 2026"
WebSearch: "медианный CPL новостройка комфорт Санкт-Петербург 2026 бенчмарк"
```

Конструктор запроса:
```
"<метрика: CPL|CPC|CPM> <канал> <тип объекта: новостройка|апартаменты|БЦ> <класс> <локация> <год> <кейс|тариф|бенчмарк>"
```

После поиска — открыть 1–2 первоисточника через WebFetch, взять диапазон, не одну точку. Источники приоритета: открытые отраслевые издания и кейсы (Cossa, Sostav, vc.ru), официальные тарифы площадок (Циан, Авито, VK Ads), отраслевые отчёты (Mediascope, AdMetrix), профильные Telegram/каналы по недвижимости (NF, ЕРЗ).

### 3.2. Поиск кейсов конкурентов в локации

Цель: найти, как продвигались сопоставимые объекты в той же локации/классе — для калибровки сегментов, каналов и углов.

```
WebSearch: "рекламная кампания ЖК комфорт Приморский район Санкт-Петербург кейс продвижение"
WebSearch: "застройщик намывные территории Финский залив маркетинг новостройка кейс"
WebSearch: "цена за метр новостройка комфорт Беговая Приморский район СПб 2026"
WebSearch: "продвижение апартаментов СПб медиа-микс кейс застройщик"
```

Конструктор запроса:
```
"<тип объекта> <класс> <микролокация/район> <город> <кейс|продвижение|медиа-микс|цена за метр>"
```

> Реплика Прохора: «Кейс соседнего ЖК — это не наш план, это репер. Я смотрю, какие каналы у них зашли и где они спотыкнулись, а решение под наш демо-объект собираю сам.»

### 3.3. Проверка трендов рынка

Цель: подтвердить/опровергнуть макро-тезис, влияющий на стратегию (ставка, спрос, ипотечные программы, absorption по сегменту).

```
WebSearch: "тренды рынка новостроек Санкт-Петербург 2026 спрос комфорт-класс"
WebSearch: "семейная ипотека условия 2026 ставка новостройка"
WebSearch: "IT-ипотека 2026 условия лимит ставка"
WebSearch: "absorption rate темпы продаж новостройки СПб 2026 статистика"
WebSearch: "доля студий первичный рынок СПб 2026 спрос"
```

Конструктор запроса:
```
"<тренд: спрос|ставка|ипотечная программа|темп продаж> <сегмент> <локация> <год> <статистика|условия>"
```

Тренд-вывод без подтверждённого источника = `[◐ гипотеза для A/B]`, не факт. Цифру по ипотечной ставке/условиям — обязательно через WebFetch первоисточника (банк, ДОМ.РФ, профильное издание), потому что условия программ меняются и устаревают быстро.

## 4. Что делать с полученным числом: статус и оформление

После актуализации каждое число оформляется как объект и встраивается обратно в карточку канала в соответствующем файле `library/channels/<категория>.yaml` (или в артефакт сессии) по канонической схеме с обновлённой `дата_актуализации`.

| Что нашли | Статус-токен | Как оформить |
|---|---|---|
| Диапазон подтверждён открытым первоисточником через WebFetch | `[✓ источник]` | значение-диапазон + ссылка + `актуализировано YYYY-MM-DD` |
| Число только в сниппете WebSearch, первоисточник не открыт | `[△ требует подтверждения]` | значение + запрос + дата + пометка «подтвердить первоисточником» |
| Экстраполяция / допущение | `[◐ гипотеза для A/B]` | значение + основание гипотезы, в бюджет не закладывать как факт |
| Источник не найден | — | строка «нет надёжных данных, требует пилота» |
| AI-визуал | `[▢ AI-визуализация]` | не относится к числам, но статусная логика та же |

### Обновление карточки канала (фрагмент YAML)

Карточка канала живёт в одном из 5 категорийных файлов `library/channels/<категория>.yaml` (performance, social, classified, brand-offline, commercial-b2b-hospitality) — единого `library/channels.yaml` нет. При актуализации бенчмарка переписываем блок `бенчмарки_2026` в карточке нужного канала внутри соответствующего файла `library/channels/<категория>.yaml`, а также в сводном `library/benchmarks.yaml` — диапазон, источник, дата. Источник «Perplexity-запрос» из старого драфта заменяется на реальный путь актуализации (WebSearch/WebFetch + домен первоисточника).

```yaml
бенчмарки_2026:
  CPL_ЖК_комфорт: 1500–4500 ₽
  источник: "WebSearch + WebFetch (домен первоисточника); ранее Perplexity"
  запрос: "CPL Яндекс Директ новостройка комфорт-класс СПб 2026"
  дата_актуализации: 2026-06-04
  статус: "[△ требует подтверждения]"   # пока первоисточник не открыт WebFetch
```

> Примечание: в существующих карточках библиотеки поле `источник` могло ссылаться на Perplexity (наследие паспорта v1.0). При любой актуализации это поле приводится к реальному пути WebSearch/WebFetch. Perplexity остаётся допустимым значением только если пользователь подключил MCP и им реально воспользовались.

## 5. Процедура «было → стало» при обновлении бенчмарка

Когда обновляем число, которое уже есть в библиотеке, не подменяем молча — показываем дифф. Это требование ядра доверия и одновременно делает обновление прозрачным.

Формат вывода:
```
Канал: <название>
Метрика: <CPL/CPC/CPM>
Было:  <старое значение> (источник, дата_актуализации старая)
Стало: <новое значение>  [✓ источник | △ требует подтверждения]
Источник: <домен первоисточника> через WebFetch
Дата:  актуализировано YYYY-MM-DD
Дельта: <направление и величина: +/- %>
```

> Реплика Прохора: «Если CPL подрос на 20% за квартал — это не повод паниковать, это повод пересмотреть долю канала. Но сначала покажу вам „было / стало“, а решение по бюджету за вами.»

---

## 6. Фолбэк-протокол (сеть упала / источник не открылся)

Порядок действий при отказе живого источника:

1. **WebFetch не открыл URL** → пробуем альтернативный первоисточник из выдачи WebSearch.
2. **WebSearch без надёжного результата** → берём значение из соответствующего файла `library/channels/<категория>.yaml` / `library/benchmarks.yaml` с его собственной (возможно устаревшей) `дата_актуализации` и явной пометкой «из кэша, не актуализировано сегодня».
3. **В кэше тоже нет** → строка «нет надёжных данных, требует пилота». Точка. Не достраиваем.

Никогда не выдаём кэш-число как свежеактуализированное. Если оно из библиотеки — несёт свою старую дату и пометку кэша.

> Реплика Прохора: «Сеть отвалилась — не страшно. Беру цифру из библиотеки, но честно говорю: она от такого-то числа, сегодня я её не трогал. Свежесть подделывать не буду.»

## 7. Связь с пайплайном

- **Этап 1 (анализ ЦА, absorption):** тренд-проверки спроса по сегменту (раздел 3.3) питают приоритизацию сегментов; absorption-вердикт считается из 3 чисел объекта, а не из веба — веб только подтверждает рыночный темп как репер.
- **Этап 1–2 (каналы, медиа-микс):** актуализация CPL/CPC/CPM (раздел 3.1) уточняет ранжирование каналов; бюджет — в долях.
- **Этап 2 (концепция):** кейсы конкурентов в локации (раздел 3.2) калибруют углы под стадию жизненного цикла.
- **Этап 3 (тексты):** проверка актуальных ипотечных условий перед упоминанием в креативе (раздел 3.3) — связка с юрфильтром 214-ФЗ: цена/ипотека без актуальных условий банка не выходит.
- **Финал (аудит-стена):** все `[✓]` / `[◐]` / `[△]`, проставленные при актуализации, автоматически собираются в стену «Чего Прохор НЕ выдумал».

- [ ] Если источника нет — написано «нет надёжных данных, требует пилота» вместо догадки?
- [ ] Гипотеза помечена `[◐ гипотеза для A/B]`, а не выдана за факт?

## 9. Отбор конкурентов: первичка, оси поиска, перекрёстная проверка

Самая частая ошибка — натащить в конкуренты вторичку и сданные-распроданные дома или
неверно определить застройщика. Конкурент засчитывается только при выполнении **всех
четырёх** критериев одновременно:

1. **Квартиры продаются ОТ ЗАСТРОЙЩИКА сейчас (первичный рынок).** НЕ конкурент, если
   дом сдан и застройщик распродал остаток, а квартиры предлагают только риелторы /
   переуступка / вторичка.
2. **Тот же район** (или вплотную по локации/метро).
3. **Сопоставимая инфраструктура.**
4. **Сопоставимые условия приобретения** (ДДУ/эскроу, ипотечные программы первички).

### Как определять «продаётся от застройщика» (главный навык)
- **Сайт застройщика:** объект в активном каталоге с доступными лотами, ценами и формой заявки.
- **Классифайды** (Циан, Домклик, Яндекс Недвижимость, Новострой): блок «Квартиры от
  застройщика» с количеством > 0 и статусом «новостройка», а не только «переуступка/вторичка».
- **ЕРЗ.РФ:** статус объекта (строится / введён) и число квартир в продаже от застройщика.
- **Дата сдачи — красный флаг:** сдан несколько лет назад + нет каталога застройщика => вторичка.

### Оси поиска кандидатов (не одна улица!)
- **Гео:** улица + РАЙОН + МЕТРО (соседние станции, радиус).
- **Застройщик-тир:** проекты тех же девелоперов рядом (часто один бренд держит несколько ЖК).
- **Смежный класс с пересечением по цене:** комфорт, входящий дешевле нашего бизнеса, —
  именно он подрезает цену входа.
- **ЗАПРЕТ:** «только по позиционированию/классу» как единственная ось — даёт слишком
  широкий и нерелевантный список. Берём лишь тех, кто совпал ещё и по гео + первичке.

### Протокол перекрёстной проверки
- Минимум **3 типа источников** на кандидата (сайт застройщика + ≥1 классифайд + ЕРЗ).
- При сомнении или нехватке данных — кандидат **отклоняется** (консервативно).
- Перепроверять застройщика отдельно (легко ошибиться: напр. БелАрт — РСТИ, а не RBI).
- В паспорт выносить и **отклонённых с причиной** — прозрачность для заказчика.

### Рейтинги и репутация
Подтягивать оценки с карт и классифайдов (2ГИС, Яндекс Карты, Циан, Домклик, Новострой,
ЕРЗ) с источником и датой (плавают). Часть площадок отдаёт рейтинг через JS/антибот —
брать дублирующие агрегаторы. Синтез отзывов в 4 слоя: объективные плюсы / объективные
минусы / эмоции (+) / эмоции (−). Это вход для барьеров и месседжей на этапе 2.
