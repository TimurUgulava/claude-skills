# Шаблоны вывода артефактов Прохора

Эталоны четырёх базовых артефактов пайплайна (этапы 1–4) плюс расширенный экспорт в Google Workspace и финальная аудит-стена. Артефакт — **сухой профэталон**: голос Прохора (деловой, средне-жёсткий, спорящий) живёт в нарративных репликах вокруг артефакта, а внутри таблиц и карточек — только данные. Спор и аргументация — на контрольных точках, не в ячейках.

Сквозной инвариант: **каждое содержательное число или факт несёт токен источника** (словарь — `references/communication-style.md`). Числа без источника не выходят. Сокращённая легенда токенов для шаблонов:

| Токен | Смысл |
|---|---|
| `[✓ источник: <откуда>, <дата>]` | verified-library или подтверждённый факт брифа |
| `[web: <домен>, <дата>]` | живой WebSearch/WebFetch на момент сессии |
| `[◐ гипотеза → A/B]` | предположение, проверяется тестом, не факт |
| `[△ требует подтверждения]` | собрано в режимах B/C, подтверждает заказчик |
| `[▢ AI-визуализация]` | изображение сгенерировано, не фото объекта |

Демо-объект сквозных примеров — условный ЖК комфорт-класса (Приморский р-н СПб, стадия монолита, 1-я очередь). Все числа примеров для демо идут со статусом `object-claim` (заявлено застройщиком) или `△`, а не как рыночный факт.

---

## Экспорт в фирменный .docx и структура проекта

Каждый этап = отдельный фирменный артефакт (модель Геннадия), а не один общий документ. Артефакты складываются в **папку проекта** с номером этапа в имени: `01-passport`, `01-competitors`, `02-audiences`, `03-concept`, `04-texts` (+ внутренний `04-texts-qa`). Рендер MD → .docx в фирменном стиле (оранжевый #FE9901, Calibri, зебра-таблицы, настраиваемый footer через `--footer`, вставка картинок из MD `![](path)`) — скрипт `scripts/export_docx.py`:

```
python3 scripts/export_docx.py 01-passport.md --output 01-passport.docx \
  --title "МАРКЕТИНГОВЫЙ ПАСПОРТ ОБЪЕКТА" --subtitle "<объект>" --meta-json '{...}'
```

Дисциплина токенов в режимах B/C: на артефакте — один общий дисклеймер «данные из открытых источников, на подтверждение заказчиком», инлайн-пометку оставляем только на DEMO-значениях. Внутренние проверки в клиентский .docx не идут (внутренняя кухня — в отдельный qa-файл).

## Артефакт 0. Паспорт объекта (вход, режимы B/C)

Самостоятельный артефакт-валидатор: первое, что показываем заказчику, чтобы подтвердить факты до работы. Ёмко, но информативно — 11 разделов:

1. Идентификация (объект, застройщик + юрлицо/ОГРН, класс, тип, стадия, сайт)
2. Локация и окружение (адрес, район, метро, инфраструктура, экология, минусы локации)
3. Архитектура и масштаб (корпуса, этажность, квартиры, двор, паркинг, энергоэффективность)
4. Квартирография и цены (типы, площади, доли, отделка, цена за м²)
5. Условия покупки и ипотека (реальные программы/ставки из хабов застройщика; юрконтур ДДУ/ДКП)
6. УТП (сгруппированы по смыслу)
7. Конкурентное окружение — коротко (прямые / массовый фон / по позиционированию / отклонённые с причиной). Только первичка от застройщика; отбор и перекрёстная проверка — `references/research-actualization.md` §9
8. SWOT (S/W внутренние, O/T от конкурентного поля) — вход для отстройки на этапе 2
9. Репутация и рейтинги (оценки с карт/классифайдов + синтез отзывов: плюсы/минусы/эмоции)
10. Темп продаж (absorption) — при отсутствии реальных чисел DEMO-значения с пометкой
11. Белые пятна на подтверждение заказчиком

Стадия: разводить «сдан» (построен/принят) и «заселение» (выдача ключей) — не обещать «въезд сейчас» без старта заселения. Класс — маркетинговый ярлык, не лестница: отстройку строим на фактах и готовности, а не на «бизнес выше комфорта». Глубокий конкурентный анализ с источниками — в отдельный файл `01-competitors`.

## Артефакт 1. Карта аудитории (этап 1)

> Подача (по фидбэку): для заказчика карту ЦА оформляем НАРРАТИВОМ — по каждому сегменту три вопроса простым языком (кто это / почему купят у нас / где искать), плюс отдельный блок «данные для таргетолога» (гео, возраст, интересы, ключевые запросы, площадки). Плотные матрицы «чек×цикл×конкуренция» в клиентский документ не выносим. Можно добавить AI-портрет каждого сегмента (GPT Image 2). Блоки A/B/C ниже — внутренняя логика; в .docx идёт нарративная версия.

Выдаётся в чате после анализа аудитории и absorption-вердикта, до контрольной развилки.

### Шапка

```
КАРТА АУДИТОРИИ
Объект: <название>, <класс>, <локация>
Тип: <object_type>  |  Стадия жизненного цикла: <котлован/монолит/отделка/сдача/остатки>
Режим входа: <A/B/C/D>  |  Статус данных объекта: <object-claim из брифа | △ требует подтверждения>
Дата сборки: <YYYY-MM-DD>
```

### Блок A. Absorption-вердикт (управленческий)

Сначала вердикт — он задаёт приоритет сегментов ниже. Формула и пороги — `references/pipeline.md`, этап 1, пункт «Absorption-вердикт».

| Параметр | Значение | Источник |
|---|---|---|
| Объём экспозиции (лотов) | 640 | `[✓ источник: прайс застройщика, 2026-XX-XX]` |
| Продано за период | 180 за 6 мес | `[✓ источник: данные РОПа]` |
| Темп продаж | ~30 лотов/мес | расчёт |
| Остаток лотов | 460 | расчёт |
| Плановый срок сдачи | 4 кв. 2027 | `[△ требует подтверждения]` |
| Остаток месяцев до сдачи | ~N | расчёт |
| Темп для равномерной распродажи | ~M лотов/мес | расчёт |

**Вердикт:** `темп ниже / в плане / выше плана` → `давим конверсию и спецусловия | держим курс | снимаем performance-газ, готовим brand под след. очередь`.

**Следствие для каналов и сегментов:** 1–2 строки, как вердикт меняет приоритет (например: «темп ниже плана → performance + classified вперёд premium-brand, горячие сегменты в приоритет, ипотечные программы в первую линию»).

### Блок B. Сегменты ЦА (4–6 штук)

Карточка на каждый сегмент. Триггеры/барьеры — отраслевые, не общие (карточки сегментов с полями `триггеры_покупки`/`барьеры` — в `library/audiences.yaml`).

```
СЕГМЕНТ <N>: <короткое имя, напр. «Семья с детьми, первичный апгрейд»>
Доля внимания: <приоритет: ядро / вторичный / тестовый>
JTBD: <работа, которую нанимают объект выполнить — одной фразой>
Триггеры (2–3): <школа в пешей доступности; двор без машин; евро-планировка>
Барьеры (2–3): <«успею ли до 1 сентября»; «не станет ли двор парковкой»; ипотечная ставка>
Ценовое восприятие: <гипотеза> [◐ гипотеза → A/B]
Релевантные каналы (из библиотеки): <classified, performance — со ссылкой на library/channels>
Связь с absorption-вердиктом: <почему этот сегмент в приоритете при текущем темпе>
```

**Правило сегментов:** не «семьи 30–40 лет», а сегмент с JTBD и конкретным триггером под тип объекта. Если в брифе сегмент не подтверждён данными — гипотезы помечаются `[◐ гипотеза → A/B]`, размер/платёжеспособность сегмента без источника не указывается.

### Блок C. Реплика Прохора (нарратив, не часть артефакта)

Здесь — голос: где Прохор спорит с приоритетом, что считает ошибкой, на чём настаивает. Пример тона: «Студии 24 м² без отделки — это не инвест-продукт, это первое жильё. Поставишь сюда таргет инвестора — сольёшь бюджет на нерелевантной аудитории. Финальное слово твоё, но я бы держал инвестора тестовым, а не ядром».

→ Дальше контрольная развилка через AskUserQuestion (А/Б/В), формулировки — `references/pipeline.md` этап 1.

## Артефакт 2. Концепция кампании (этап 2)

Выдаётся после развилки этапа 1, под выбранный приоритетный сегмент. Привязана к стадии жизненного цикла (логика стадий — `references/pipeline.md`, этап 2, пункт «Позиционирование под стадию жизненного цикла»).

### Шапка

```
КОНЦЕПЦИЯ КАМПАНИИ
Объект: <название>  |  Приоритетный сегмент: <из развилки этапа 1>
Стадия жизненного цикла: <монолит — аргументация: ход стройки, темп, эскроу как гарантия>
Absorption-вердикт (наследуется): <давим конверсию | снимаем газ>
Дата: <YYYY-MM-DD>
```

### Блок A. Позиционирование

```
Позиционирование: <одна формулировка — кто мы для этого сегмента на этой стадии>
Обоснование стадией: <почему именно этот посыл на стадии монолита, а не абстрактно>
УТП-опора: <видовые квартиры на залив; набережная с велодорожкой; своя школа>
  — каждое УТП-число со статусом: [✓ источник] / [△ требует подтверждения]
```

### Блок B. Ключевые сообщения (key messages)

| № | Сообщение | Под триггер сегмента | УТП-опора и источник |
|---|---|---|---|
| 1 | <message на профжаргоне> | <триггер> | <факт> `[✓ источник]` или `[△]` |
| 2 | … | … | … |
| 3 | … | … | … |

**Правило:** сообщение с числовым УТП (метраж, время до метро, доля студий) несёт источник. УТП без подтверждённого факта — `[△ требует подтверждения]`, на сцене и в проде не подаётся как факт.

### Блок C. Креативные углы (3–5)

```
УГОЛ <N>: <название>
  Триггер: <на что давит>
  Доказательство: <чем подкреплён> [✓ источник / △]
  Под формат: <performance / social / classified / brand-offline>
```

Угол = триггер + доказательство. Доказательства-числа — со статусом источника. Углы без фактической опоры (только эмоция) помечать как brand-гипотезу.

### Блок D. Tone-of-voice

```
ToV под сегмент <X> и канальную категорию <Y>:
  Регистр: <деловой / тёплый-семейный / статусный — без инфоцыганщины>
  Лексика: <профжаргон уместен / упрощаем под массовый сегмент>
  Запреты ToV: <без превосходных степеней, без обещаний доходности/роста цены>
```

### Блок E. Медиа-приоритет (наследуется из absorption)

Короткий ранжированный список канальных категорий под вердикт. При «давим конверсию» — performance/classified вперёд premium-brand. Доли бюджета — только в опции «медиа-микс» и только в %, не в рублях.

→ Контрольная развилка этапа 2 (2 маршрута позиционирования + слот «свой»), формулировки — `references/pipeline.md`.

## Артефакт 3. Пакет текстов по сегментам и форматам (этап 3)

Выдаётся после двойной проверки (антимодерация площадок + юрфильтр 214-ФЗ). Все тексты уже прошли оба слоя; нарушения переформулированы по схеме «было → стало».

### Шапка

```
ПАКЕТ ТЕКСТОВ
Объект: <название>  |  Сегмент: <приоритетный>  |  Концепция: <название>
Форматы в пакете: <performance / social / classified / brand-offline>
Проверки пройдены: антимодерация площадок ✓ + юрфильтр 214-ФЗ ✓
Дата: <YYYY-MM-DD>
```

### Блок A. Таблица текстов

Имена столбцов «Формат_1/2» подменяются на конкретные площадки (`ЯД_Поиск_Заголовок`, `VK_Текст`, `Авито_Заголовок`).

| № | Сегмент | Формат_1_Заголовок | Формат_1_Текст | Формат_1_CTA | Формат_2_Заголовок | Формат_2_Текст | Флаги проверки | Связь с креативом |
|---|---|---|---|---|---|---|---|---|
| 1 | <сегмент> | <заголовок ≤ лимита> | <текст ≤ лимита> | <CTA> | <адаптация> | <текст> | `чисто` / `переформулирован — см. блок B` | `→ креатив #N` |

**Правила таблицы (профэталон, без реплик):**
- все столбцы заполнены, пустых ячеек нет; нет картинки/CTA → ставим `—` и сообщаем отдельно;
- каждый текст содержит объект (название ЖК) и проходит лимиты площадки;
- маркировка ОРД/`erid` — отдельным полем или пометкой, если кампания идёт в проде.

### Блок B. Лог «было → стало» (что и почему переформулировано)

На каждый сработавший флаг — пара до/после рядом, с точной ссылкой на правило. Это рабочий лог для юротдела, а не украшение.

| № | Было (сырой) | Флаги (слой 1 / слой 2) | Стало (легальный, тот же драйв) | Норма-ссылка |
|---|---|---|---|---|
| 1 | «Инвестируй в апартаменты — доходность 14% годовых!» | антимодерация: превосх./стоп-слово; 214-ФЗ: обещание доходности, «не жильё», нужна декларация | «Апарт-комплекс в локации с растущим арендным спросом. Ассет-менеджмент от УК» `[△ числовые обещания убраны]` | ФАС о доходности; ст. 214-ФЗ; правило площадки |

**Разделение слоёв (фиксируется в флагах):**
- **слой 1 — антимодерация площадок** (`references/moderation-rules.md`): стоп-слова Директа/VK/Telegram, «лучший»/«номер 1» без подтверждения, превосходные степени;
- **слой 2 — юрфильтр 214-ФЗ** (надстройка Прохора): запрет обещаний доходности и прироста цены (строже для апартов/ДДУ), «апартаменты ≠ квартира», цена/ипотека без проектной декларации и банка/условий, «от застройщика» без юрлица/ОГРН, маркировка ОРД/`erid`.

### Блок C. Реплика Прохора (нарратив)

Здесь — комментарий, где Прохор объясняет, почему не выкинул креатив, а переформулировал, и что осталось на ответственности заказчика. Сухие данные — в таблицах выше.

→ Контрольная точка: пользователь утверждает пакет или правит.

## Артефакт 4. Пакет визуалов (этап 4)

Выдаётся после генерации через Nano Banana / GPT Image 2. По умолчанию графика отдаётся чистой, без знака на самом изображении. Маркировка «это AI-картинка, а не фото объекта» живёт текстовым токеном `[▢ AI-визуализация]` в артефакте рядом с картинкой, а не в пикселях. Впечатать watermark в пиксель — опционально, только по явному запросу заказчика. Изображения лежат локально, в выдаче каждое помечено токеном `[▢ AI-визуализация]`.

### Шапка

```
ПАКЕТ ВИЗУАЛОВ
Объект: <название>  |  Сегмент / концепция: <…>
Форматы: 1:1, 4:5, 9:16, 16:9 (+ расширенные по опции: DOOH 6:1, 3:4)
Маркировка: токен [▢ AI-визуализация] рядом с картинкой (графика чистая; впечатать watermark в пиксель — опция по запросу заказчика)
Папка: ~/Downloads/images/prohor/<slug>   (демо-объект: zhk-demo)
Дата: <YYYY-MM-DD>
```

### Блок A. Таблица визуалов

| № | Креатив-связь | Формат | Модель | Обоснование роутинга | Промпт (свёрнут) | Файл | Маркировка |
|---|---|---|---|---|---|---|---|
| 1 | `← текст #N` | 16:9 | Nano Banana | атмосфера, dusk-фасад, свет среды | `<полный промпт>` | `<абс. путь>.png` | `[▢ AI-визуализация]` |
| 2 | `← текст #M` | 1:1 | GPT Image 2 | кириллический постер «Старт продаж», цена числами | `<полный промпт>` | `<абс. путь>.png` | `[▢ AI-визуализация]` |

**Правила (профэталон):**
- роутинг модели обосновывается под задачу: Nano Banana — атмосфера/свет/среда; GPT Image 2 — текст на изображении, кириллица, цена на плашке;
- по умолчанию графика отдаётся чистой, без знака на самом изображении. Маркировка «это AI-картинка, а не фото объекта» живёт текстовым токеном `[▢ AI-визуализация]` в артефакте рядом с картинкой, а не в пикселях. Впечатать watermark в пиксель — опционально, только по явному запросу заказчика, фиксируется в логе;
- если креатив построен **по референсу** (оригинал объекта — рендер с сайта / ассет заказчика), указываем источник референса в логе и в `campaign_matrix`; результат всё равно `[▢ AI-визуализация]`, права на исходник — на заказчике (`references/image-generation.md`, «Генерация по референсам»);
- если генерация упала — в столбце «Файл» ставим `—`, фолбэк-описание промпта остаётся, сообщаем отдельно.

### Блок B. Реплика Прохора (нарратив)

Профразбор: какая модель что отрисовала, где текст «поплыл», что брать под баннер с ценой. На сцене — момент дуэли (`references/demo-mode.md`), в проде — рабочий комментарий к выбору.

## Аудит-стена «Чего Прохор НЕ выдумал» (финал сессии)

Собирается автоматически из проставленных по всем артефактам токенов. Переворот логики: неуверенность не прячется, а выставляется как чек-лист перед запуском бюджета.

```
СТЕНА ИСТОЧНИКОВ
─────────────────────────────────────────────
Источников проставлено: <N>   [✓ verified-library + web]
Живых WebSearch/WebFetch за сессию: <K> (домены: …, даты: …)

◐ ГИПОТЕЗЫ (не факт, требуют A/B-теста):
  • <гипотеза 1>
  • <гипотеза 2>

△ ДАННЫЕ НА ПОДТВЕРЖДЕНИЕ ЗАКАЗЧИКОМ:
  • <факт объекта 1 — собран в режиме B/C>
  • <цена/срок сдачи — требует прайса/декларации>

▢ ВИЗУАЛЫ ПОМЕЧЕНЫ [▢ AI-визуализация]: <M> штук
─────────────────────────────────────────────
Что проверить до запуска бюджета: <короткий чек-лист>
```

Правило: число в счётчике источников должно сходиться с реально проставленными токенами в артефактах. Стена — не декларация, а свод. Подробности демо-подачи — `references/demo-mode.md`.

## Расширенный экспорт в Google Workspace (опция, раздел 11 паспорта)

Включается командой «выгрузи в Google». Делегируется скиллу `google-workspace-pro` (Skill tool). Собирается папка на Drive со всеми артефактами под передачу команде/подрядчику.

### Состав папки

```
<Название кампании> — <объект> — <дата>/
├── strategy.gdoc           — стратегический документ
├── campaign_matrix.gsheet  — матрица сегмент × канал × формат
├── creatives/              — все визуалы (PNG, графика чистая; маркировка токеном [▢ AI-визуализация] рядом)
├── briefs/                 — брифы под подрядчиков
└── README.gdoc             — инструкция по запуску + чек-лист модерации + точки A/B
```

### strategy.gdoc

Один документ, восстанавливающий логику кампании за 5 минут без захода в чат:

1. Паспорт объекта (со статусами данных: `object-claim` / `△`)
2. Absorption-вердикт (3 числа + источники + следствие для каналов)
3. Карта аудитории (сегменты, JTBD, триггеры, барьеры)
4. Концепция (позиционирование под стадию, key messages, креативные углы, ToV)
5. Медиа-приоритет / медиа-микс (доли %, не рубли) — если опция включена
6. Воронка длинной сделки с лагами эскроу/ДДУ — если опция включена
7. Аудит-стена (источники, гипотезы, данные на подтверждение)

### campaign_matrix.gsheet

Делегируется `google-workspace-pro`. **Две обязательные вкладки** (как у Кеши: первая — контекст, вторая — данные).

**Вкладка 1 «Бриф»** (двухколоночная: лейбл / содержимое; секции — заголовки на всю ширину, оранжевая заливка `#FF9900`, белый жирный 12pt, merge A:B):

1. Объект — название, класс, локация, стадия, статус данных
2. Absorption-вердикт — 3 числа, темп, остаток, вывод
3. Сегменты ЦА — приоритет, JTBD, распределение внимания
4. Главный триггер сегмента и барьеры (как нейтрализуем)
5. Концепция — позиционирование, key messages, креативные углы, ToV
6. Юрчек 214-ФЗ — что переформулировано и почему (резюме лога «было → стало»)
7. Дизайн-код визуалов — стиль, свет, форматы, роутинг моделей, маркировка [▢ AI-визуализация]
8. Площадки — что куда (категория → объявления N..M на вкладке «Матрица»)
9. Что проверить до запуска — модерация на грани, проектная декларация, ОРД/erid, точки A/B

**Вкладка 2 «Матрица»** — таблица сегмент × канал × формат с текстами и ссылками на креативы:

| Столбец | Содержимое |
|---|---|
| № | Порядковый номер |
| Сегмент | Приоритетный сегмент ЦА |
| Канал | Канал из `library/channels/` (категория + channel_id) |
| Этап воронки | лидген / конверсия / охват / ремаркетинг |
| Формат | 1:1 / 4:5 / 9:16 / 16:9 / текстовое объявление |
| Заголовок | Текст заголовка под формат |
| Текст | Тело объявления |
| CTA | Призыв |
| Статус юрчека | `чисто` / `переформулирован` |
| Промпт визуала | Полный промпт генерации |
| Референс / основа | Источник оригинала, если креатив построен по референсу (рендер с сайта / ассет заказчика); пусто — генерация с нуля |
| Картинка | Rich text link «Открыть» на файл в Drive (не формула HYPERLINK — нестабильна в ru_RU) |
| Маркировка | Токен `[▢ AI-визуализация]` (графика чистая; впечатать watermark в пиксель — опция по запросу заказчика) |
| Источники чисел | Токены `[✓]` / `[web]` / `[△]` по строке |

Правила: все ячейки заполнены, пустых нет; нет картинки → `—` и отдельное сообщение; гиперссылки — rich text link через Sheets API (формула `=HYPERLINK` нестабильна в локали ru_RU), реализует `google-workspace-pro`.

### creatives/

Все PNG из `~/Downloads/images/prohor/<slug>` заливаются в подпапку Drive. **По умолчанию графика отдаётся чистой, без знака на самом изображении.** Маркировка «это AI-картинка, а не фото объекта» живёт текстовым токеном `[▢ AI-визуализация]` в артефакте рядом с картинкой (вкладка «Матрица», бриф дизайн/AI-продакшн), а не в пикселях. Впечатать watermark в пиксель — опционально, только по явному запросу заказчика. Картинку нельзя выдавать за фото объекта.

### briefs/

Отдельные брифы под подрядчиков (каждый — короткий gdoc):

- **медиа-байер** — каналы, доли %, этапы воронки, absorption-вердикт как обоснование, правило «не убивай канал на второй неделе» (лаг эскроу/ДДУ);
- **дизайн/AI-продакшн** — дизайн-код, форматы, роутинг моделей, правило маркировки (графика чистая; токен `[▢ AI-визуализация]` рядом с картинкой; впечатать watermark в пиксель — опция по запросу заказчика), что можно/нельзя править;
- **фото/видео-продакшн** — что снять вживую вместо AI-визуализаций перед реальным запуском (закрывает риск «AI выдают за фото»).

### README.gdoc

Инструкция по запуску: порядок включения каналов, чек-лист модерации (слой 1 + слой 2), обязательная маркировка ОРД/`erid`, точки A/B-тестов (все `[◐ гипотеза]` из аудит-стены), напоминание о валидации `[△]`-данных и проектной декларации до старта открутки.

### Шаринг и финал

После сборки — `permission: anyone with link, role: reader` на папку, sheet, doc и каждый файл картинки (иначе ссылки работают только у владельца). В чат — ссылки на папку и матрицу + строка про доступ.
